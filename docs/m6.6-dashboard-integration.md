# M6.6 — Dashboard and end-to-end workflow integration

**Status:** implemented, tested and exercised against the real on-disk M6.3
artifacts in this checkout. Real M6.4/M6.5 results still do **not** exist; the
dashboard now says so explicitly instead of showing nothing.

This document records what M6.6 added, what it deliberately did not do, and the
**scope reconciliation** between the original M6 objective and the method that was
actually implemented.

---

## 1. Scope reconciliation (read this before quoting any M6 result)

### 1.1 Original direction

The M6 direction was a **supervised multimodal Sentinel-1 / Sentinel-2 flood
segmentation** model: paired optical and SAR inputs, flood labels, and an
accuracy figure.

### 1.2 What the project actually established

The optical/dataset feasibility work (`docs/m6.2-sentinel2-optical-validation.md`,
`docs/m6.2-catalogue-requery.md`, `docs/dataset-registry.md`,
`docs/m4-architecture-decision.md`) found that **no permitted training corpus
available to this project satisfies the full requirement set** — paired optical
imagery, flood/permanent-water labels, and a pre/post temporal structure:

* the two permitted corpora label `{no water, permanent water, flood, invalid}`
  and `{no data, not water, water}`; **neither labels debris or sediment**
  (`README.md` §14);
* **Sen1Floods11 has no pre-event image**, so optical *change* cannot be
  supervised at all (`docs/m4-architecture-decision.md` §74);
* the corpora disagree on SAR representation (linear σ⁰ vs dB), so a naive union
  is forbidden;
* no Sentinel-2 granule satisfying the current single-scene coverage gate was
  found for this corridor, so optical *pixels* for the Trishuli AOI were never
  obtained (`docs/m6.2-catalogue-requery.md` §4).

### 1.3 What is implemented instead

M6.3 is a **real-SAR change-candidate method over RTC γ⁰ inputs**, not a trained
flood segmentation model. It computes VV/VH log-ratio change in dB and applies an
explicit dual-polarisation darkening rule (`configs/rtc_change_candidates.yaml`).
Its output is *candidate change evidence*.

**M6.6 does not change that and does not claim otherwise.** Specifically, the
following are **NOT** achieved and must not be described as achieved:

| Not claimed | Why |
|---|---|
| Optical fusion | No optical pixels for the AOI; no paired corpus |
| Supervised multimodal Sentinel-1/Sentinel-2 training | No permitted dataset with the required structure |
| Flood accuracy / IoU / Dice for Trishuli | No independent reference labels; no trained model applied |
| Validated flood segmentation | The candidate rule is exploratory and unvalidated |
| Sigma-0 equivalence | M6.3 inputs are γ⁰ linear power; the M5 baseline consumed σ⁰ |
| Infrastructure damage or settlement isolation | M6.4/M6.5 produced no real artifacts |

The dashboard surfaces these as **limitations**, not as footnotes: the candidate
layer is tiered `observed_derived` (a rule applied to observed SAR) and is
labelled "rule-based" in its title and provenance, never as a prediction.

## 3. Artifact discovery and validation

`discover_m63_artifacts()` resolves `artifacts/m6_3/rtc_change_candidates/`
**relative to the repository root** (`resolve_project_root()`: explicit path →
`FLOODMAP_PROJECT_ROOT` → module location, sanity-checked against
`pyproject.toml`). The working directory is never consulted, so the app behaves
identically wherever it is launched.

It then checks, and reports individually:

* **Presence** of all seven required files (four rasters — candidate mask,
  valid mask, **AOI mask** and feature stack — summary JSON, two provenance
  YAMLs). `rtc_aoi_mask.tif` became required with the 0.2.0 contract; a set
  without it is refused, because the candidate mask's single not-observed class
  cannot otherwise be split into "outside the study extent" and "inside the
  extent but not observed".
* **Readability** — each raster is opened; a malformed summary is a parse error.
* **Band names** — `change_candidate`, `valid_change_observation`,
  `vv_change_db` + `vh_change_db`.
* **Grid alignment** — candidate mask vs valid mask vs feature stack must agree
  on CRS, shape and transform.
* **Declared metadata** — `stage == m6.3-rtc-change-candidates-0.2.0` and
  `radiometric_convention == gamma0_linear_power`; a `0.1.0` artefact is refused
  as stale rather than reinterpreted under the current contract.
* **Class values** — the candidate mask must only contain `{0, 1, 255}`; the
  valid mask and the AOI mask only `{0, 1}`; and **no candidate pixel may fall
  outside the valid-data mask or outside the AOI mask** (if it does, the rasters
  describe different things). The AOI is rasterized onto the delivered grid by
  pixel centre (`all_touched=false`, no resampling, no geometry repair) and
  intersected into validity *before* the candidate rule runs, so a candidate is
  an observed, in-extent pixel by construction.
* **Summary vs rasters** — `total_pixels`, `valid_pixels`, `invalid_pixels`,
  `candidate_pixels`, both candidate fractions and the candidate grid area are
  recomputed from the rasters and compared with `rtc_change_summary.json`; the
  AOI-scoped counts are recomputed from the masks and cross-checked against the
  required `aoi_scope` block. A result whose delivered or valid area exceeds the
  full extent area is refused.
* **Provenance** — both records must parse and declare the expected
  `ArtifactType` (`change_candidate_mask`, `feature_stack`).

The result is one of four states: `valid`, `missing`, `malformed`,
`inconsistent`. Only `valid` is rendered as a result. Anything else is shown as a
problem list, and **the synthetic demo is never substituted**.

The dashboard displays the recorded figures (from the summary) and the recomputed
figures (from the rasters) side by side and states whether they agree. The number
shown to a judge is therefore traceable to two independent readings of the same
artifacts, not to a single JSON file.

### 3.1 Scope of the area figure — four notions, never one number

Since the 0.2.0 contract the candidate mask is **AOI-scoped**, so no single
"area" figure is unambiguous. The dashboard always shows the four notions
separately, each with its own denominator, and the stage records the same
separation in `rtc_change_summary.json`:

| Notion | Value for the adopted extent | Denominator |
|---|---:|---|
| Study extent (AOI polygon) | 206.150651 km² | — it is the extent, **not** an observed area |
| Delivered observation support (AOI ∩ delivered raster window) | 130.641632 km² | 63.3719 % of the extent |
| Validity observed support (jointly valid pre/post VV+VH) | 130.6418 km² pixel-centre estimate | 100.0000 % of delivered centres |
| Darkening candidates | 4.5269 km² (45,269 px) | 3.465124 % of valid in-extent pixels; 2.195918 % of the extent as a **lower bound** |

The delivered raster window itself (3313 × 4961 at 10 m ≈ 1643.6 km²) is a
bounding-box crop, **not** the study extent: 15,129,375 of its pixels (92.0514 %)
have centres outside the AOI, and window-scope fields such as
`candidate_fraction_of_grid` and `candidate_grid_area_km2` are mechanical array
tallies over it, never extent-relative rates. The dashboard states this next to
the figures. Candidate area is not confirmed flood area. `configs/aoi/trishuli-corridor-UNVERIFIED.geojson`
(≈132.93 km²) is a replaced historical geometry and is no longer the study
extent.

## 4. Real-data dashboard contents

On the real path the app shows:

1. candidate-mask overlay (red = candidate; faint grey = observed, not
   candidate; **transparent = not observed**);
2. VV and VH log-ratio change in dB as separate diverging layers (blue =
   darkening, red = brightening), with -9999 nodata transparent;
3. acquisition dates, scene IDs, relative orbit 85 and orbit direction for both
   scenes;
4. the radiometric convention, with an explicit "γ⁰, not σ⁰; no equivalence with
   the M5 σ⁰ baseline" note;
5. CRS `EPSG:32645`, 10 m resolution, 3313 × 4961, nodata values;
6. valid-pixel count, candidate-pixel count and candidate percentage (recorded
   and recomputed);
7. candidate grid area and its exact spatial scope;
8. layer provenance (production inputs, limitations, notes, versions,
   attribution) and the full consistency-check list.

Full-resolution rasters are read for the metrics; the overlays are read decimated
to ≤1200 px on the long side purely for display. No metric is taken from the
decimated array.

## 5. M6.4 / M6.5 blockers and the workflow panel

`load_blocker_report()` reads
`artifacts/m6_4/candidate_infrastructure_exposure/candidate_exposure_blocker.json`
and
`artifacts/m6_5/candidate_network_disruption/candidate_disruption_blocker.json`
verbatim and distinguishes:

| Blocker state | Presentation |
|---|---|
| `loaded` + `status: blocked` | Reason, searched directory, missing prerequisites, authorisation gate, next steps, "explicitly not done" |
| `missing` | "No blocker report found; the reason is unknown" — never a synthesised reason |
| `malformed` | "Malformed and its contents cannot be trusted", with the parse problem |

The workflow panel reports each stage as one of: *completed on real data*,
*implemented — not executed*, *blocked on a missing prerequisite*, *missing
output*, *invalid/inconsistent output*, *unknown*. A blocked or missing stage is
never rendered as zero impact, and the panel states the ordered requirements for
real M6.4/M6.5 execution: verified/authorised AOI → permitted pre-event OSM →
M6.4 on real inputs → M6.5 on real exposure artifacts. M6.6 performs none of
them.

## 6. Real / demo separation

* The sidebar selector names the active source, and the page title and banner
  repeat it ("REAL M6.3 artifacts" vs "SYNTHETIC DEMO").
* The real path cannot reach the demo generator: `realdata`, `workflow`,
  `realbundle` and `render` contain no reference to `demobundle` or
  `build_demo_bundle`, asserted by a test.
* A missing or invalid real artifact set produces an error and the problem list.
  It never falls back to synthetic values.
* The demo bundle remains `is_synthetic = true` with `SYNTHETIC PLACEHOLDER` in
  every provenance note, and its values never enter the real metrics.
* Nodata semantics are preserved everywhere: not-observed pixels are transparent
  and are excluded from the recomputed counts' numerator and denominator
  appropriately (`candidate_fraction_of_valid` uses valid pixels, not grid
  pixels).

## 9. Limitations affecting the M6.6 result

* **No independent reference labels.** Nothing here can state candidate accuracy
  or compare against EMSR927/UNOSAT; those remain validation-only and unused.
* **Partial observation, not a bounding window.** Candidate statistics are
  AOI-scoped but cover only the delivered and validly observed 63.37 % of the
  adopted 206.150651 km² extent; 36.63 % is unobserved and carries no finding.
  The 1643.6 km² raster window is a crop that reaches far outside the extent and
  is never used as an AOI denominator.
* **γ⁰ vs σ⁰.** The M5 baseline's four channels are σ⁰; M6.3 inputs are γ⁰ linear
  power. No equivalence is claimed and no M5 checkpoint was applied. (The `models/`
  directory contains only `.gitkeep`: no checkpoint and no fitted-statistics
  artifact exist in this checkout, so M5 inference is not possible here.)
* **Rule sensitivity untested at scale.** The -3 dB threshold is an explicit
  exploratory rule; sensitivity to it has not been established.
* **M6.4/M6.5 have no real results.** Only blocker reports exist. No
  infrastructure, road, connectivity or isolation number exists anywhere in this
  repository.
* **AOI provenance remains UNVERIFIED** and `authorises_download` remains false.
  M6.6 changed neither.
