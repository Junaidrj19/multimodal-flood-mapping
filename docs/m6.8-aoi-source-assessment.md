# M6.8 — Authoritative AOI Source Assessment

**Investigation date:** 2026-10-16

**Subject:** replacement for `configs/aoi/trishuli-corridor-UNVERIFIED.geojson`

**Decision context:** Option B — replace the unrecoverable polygon with an
authoritative, independently traceable geometry rather than reconstructing or
validating it by resemblance.

**Investigation mode:** read-only. No source dataset, event vector package,
satellite product, catalogue API, or acquisition API was queried or downloaded.

## 1. Executive recommendation

### Recommendation

**Do not create or install replacement geometry yet.** The repository and the
published source records reviewed here do not establish a single organizer-
selected AOI, a canonical upstream/downstream study reach, or permission to
turn an event flood footprint into the production acquisition AOI.

The defensible path remains **Option B**, but it is not complete merely because
authoritative event maps exist. The strongest source candidates have different
roles:

1. **Organizer-provided AOI:** the preferred outcome, but no such geometry or
   persistent identifier is referenced by the repository materials reviewed.
2. **Copernicus EMSR927:** authoritative emergency-mapping AOIs and products,
   but validation-only under this project and split into multiple product AOIs;
   not a documented competition study boundary.
3. **HOT observed flood extent (27 August 2026):** a traceable, dated event
   observation in EPSG:4326, but an interpreted flood footprint rather than a
   study boundary. It is not an allowed production input.
4. **HydroRIVERS/HydroBASINS:** traceable baseline hydrography covering the
   transboundary Trishuli/Gandaki system. HydroRIVERS is a credible input to a
   *new, explicitly derived* corridor only if the challenge owner permits that
   construction and confirms the intended reach. It is not itself the required
   corridor polygon.

**Current go/no-go:** **NO-GO for replacement geometry and production
acquisition. GO for a separate human decision stage** that obtains the
organizer AOI or authorizes a documented HydroRIVERS-derived corridor.

### Confidence

* **High confidence:** the current polygon is not provenance-authoritative;
  EMSR927 and HOT event products are not interchangeable with a production
  acquisition AOI; HydroBASINS is a watershed product, not a river corridor.
* **Moderate-to-high confidence:** HydroRIVERS is the most defensible
  traceable source family for a derived analytical corridor if derivation is
  permitted.
* **Low confidence:** any claim about the intended upstream/downstream reach,
  because the official case-study extent has not been supplied in the
  repository or found in the reviewed public catalogue records.

The words **verified**, **inference**, and **human confirmation required** are
used below deliberately. Catalogue inclusion is not scientific validation; the
catalogue itself says so in its [About page](https://evelpidou.nkua.cloud/Nepal-Flood-2026-Catalogue/about/).

### 3.2 The catalogue's observed flood extent is not the study boundary

The catalogue provides an unusually useful, independently traceable record for
the requested 27 August layer:

* The asset is explicitly titled **“Observed flood extent, 27 August 2026”**.
* It is a vector GeoJSON file in EPSG:4326, with a source URL, provider, file
  size, bounds, date, and ODbL-1.0 record.
* The parent resource says the flood boundary was interpreted from multiple
  observation sources and that a 200 m surrounding margin was used to define
  the extraction area for the accompanying infrastructure layers.
* The parent resource describes a response-mapping collection across the
  Bhote Koshi, Trishuli, and downstream Narayani corridor; it does **not** say
  that the observed footprint is the official competition AOI.
* The catalogue also warns that spatial inclusion of an OSM/Overture feature is
  not proof that the feature was flooded or structurally damaged.

The defensible interpretation is therefore:

> **Observed event footprint / validation reference, not an acquisition AOI.**

It is temporally tied to one interpreted date, can omit unobserved or later
flooded areas, and does not define the complete context needed for pre-event
satellite/OSM acquisition. Using it to choose the production footprint would
also import a published event interpretation into a pipeline whose production
inputs are deliberately limited to Sentinel-1, Sentinel-2, Copernicus DEM,
pre-event OSM, and permitted training data.

No source vector was downloaded or geometrically compared in this
investigation. The catalogue bounds are metadata, not evidence that the HOT
footprint matches the old polygon or the intended judge-selected reach.

### 4.2 Conditional construction method if Option C is authorized

If the project owner confirms that the challenge permits a derived analytical
corridor, the separate implementation stage should use the following method.
This is a method recommendation, **not geometry construction performed by
M6.8**:

1. Obtain the published HydroRIVERS Asia extract and record its exact product
   version, source URL, retrieval date, provider terms, file hash, source CRS,
   and all delivered metadata. Do not use the old polygon to choose or trim
   reaches.
2. Define the intended reach in a human-readable decision record before
   selecting features: named main stem/tributary, upstream terminal reach,
   downstream terminal reach, inclusion/exclusion of Bhote Koshi branches, and
   whether the Narayani confluence is included. Prefer source reach IDs and
   documented topology/attributes over names inferred from a map.
3. Use HydroBASINS only as a documented catchment/topology cross-check. Do not
   replace a line corridor with a whole watershed or use its polygons as a
   proxy for the study area.
4. Define a new corridor rule in metres. The current polygon's 1 km declaration
   is not a requirement and must not be copied. If a buffer is scientifically
   justified, record the rationale and a sensitivity range before construction.
5. Reproject explicitly to a suitable local projected CRS, document the
   transformation, buffer the selected line network, and clip only at the
   human-approved endpoints or another explicitly named boundary. Preserve
   branches and topology decisions in provenance.
6. Export one valid GeoJSON Polygon or single-feature FeatureCollection in
   EPSG:4326, with source identifiers, source version, construction parameters,
   CRS operations, licence, attribution, and SHA-256. A generated polygon is
   **derived**, not “official”; its provenance status should say so.
7. Run geometry validity, bounds, area, and acquisition-footprint checks. The
   checks must verify that the new polygon is the intended construction result,
   not that it resembles `trishuli-corridor-UNVERIFIED.geojson`.
8. Issue a new AOI ID and update dependent manifests/configuration only in the
   separate implementation stage. Existing M6.2/M6.3 measurements remain
   historical measurements of the old unverified geometry and cannot be
   silently transferred.

### 4.3 Claims that require human confirmation

The following questions block a defensible replacement:

1. Is there an organizer-held AOI, challenge attachment, judge packet, or
   persistent identifier not present in this checkout?
2. Is the intended area the full Bhote Koshi–Trishuli–Narayani event corridor,
   a shorter Upper Trishuli reach, one or more EMS mapping AOIs, a watershed,
   or another explicitly named area?
3. What are the authoritative upstream and downstream endpoints?
4. May a derived AOI be constructed from HydroRIVERS if no organizer AOI is
   available?
5. If a derived corridor is allowed, which branches and what width or other
   cross-stream rule are required?
6. Which role owns the decision and can authorize `provenance_status: verified`
   for acquisition?

Until these are answered, no source can honestly be described as “the official
study boundary.”

## 5. Licence, attribution, and data-governance considerations

### 5.1 Source-specific terms

* **HOT/OSM/Overture:** the catalogue records ODbL 1.0 for the HOT collection.
  The collection combines sources with different upstream terms; any later
  use would need to preserve the component attribution and database rights.
  The project must continue to use the specified pre-event OSM snapshot for
  production infrastructure, not the event-response OSM/Overture layers.
* **Copernicus EMSR927:** the catalogue records the Copernicus/EU source and a
  CC BY claim through HDX, but product and source-imagery rights remain
  distinct. Regardless of licence, this project's rules make EMSR927
  validation-only.
* **HydroSHEDS:** the provider describes HydroRIVERS and HydroBASINS as freely
  available for scientific, educational, and commercial use under the
  HydroSHEDS licence agreement. Do not replace that statement with an assumed
  CC BY licence. Preserve the provider terms and cite Lehner & Grill (2013).
* **MERIT Hydro:** the catalogue records unresolved licence choices and a
  registration/password access route. It is not needed for the recommended
  first replacement path.

### 5.2 Project attributions

If the later production stage uses the project's permitted sources, it must
retain the mandatory attributions from `AGENTS.md` §18 and `configs/data.yaml`:

> Contains modified Copernicus Sentinel data 2026.

> Produced using Copernicus WorldDEM-30 © DLR e.V. 2010–2014 and © Airbus
> Defence and Space GmbH 2014–2018 provided under COPERNICUS by the European
> Union and ESA; all rights reserved.

> © OpenStreetMap contributors.

HydroSHEDS or any other derived-AOI source would additionally require its own
provider attribution and terms; it would not remove the challenge attributions
for the production inputs.

## 6. Exact next steps for a separate implementation stage

1. **Human decision / source request.** Ask the challenge organizer or named
   project owner for the canonical AOI asset or identifier, intended role,
   upstream/downstream definition, CRS, version/date, licence, and an
   authoritative retrieval URL. Record the decision in project documentation.
2. **If an organizer AOI is supplied:** retrieve only in the authorized
   implementation stage; inspect its geometry and metadata; preserve the
   original file, source URL, retrieval date, version, licence, CRS, and hash;
   convert to the application EPSG:4326 representation only with a documented
   transformation; assign a new stable AOI ID.
3. **If no organizer AOI exists:** obtain written confirmation that a derived
   AOI is allowed, then implement the HydroRIVERS procedure in §4.2. Record
   reach IDs and endpoint rules before writing geometry. Do not reuse the old
   1 km buffer or its coordinates.
4. **Keep event maps separate.** Register EMSR927 and the HOT 27 August extent
   as validation/reference sources only. Do not feed them into feature
   generation, inference, threshold selection, or production AOI selection
   without an explicit governance decision that is consistent with the
   challenge rules.
5. **Update identity atomically.** Change the AOI file path, `aoi_id`, hash,
   provenance status, and provenance gaps together. Update contract-freeze and
   acquisition tests to the new documented identity. Do not edit old manifests
   to make them appear to have used the replacement geometry.
6. **Re-run non-destructive checks first.** Run geometry checks, acquisition
   dry-run/metadata selection, CRS and coverage tests, and inspect the new
   manifest. Confirm that the event window, same-track rule, coverage threshold,
   and limitations are explicit.
7. **Only after provenance is verified:** obtain the operator's authorization,
   enable no exploratory exception, and follow the existing explicit download
   gate. Then acquire permitted pre-event OSM and satellite inputs in separate,
   auditable steps.
8. **Reassess downstream artifacts.** M6.2 SAR coverage, M6.3 change
   candidates, M6.4 infrastructure exposure, M6.5 network inference, and
   dashboard inputs must be regenerated or marked stale against the new AOI.
