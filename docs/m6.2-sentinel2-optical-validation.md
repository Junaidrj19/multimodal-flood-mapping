# M6.2 — Sentinel-2 optical validation pipeline

**Status of this document.** It distinguishes what is **implemented and tested**
from what is **planned and still needs real imagery**. Nothing here is a flood
result: these are observation-availability statistics, which are a precondition
for a flood claim and not a claim.

No Sentinel-2 product was downloaded in M6.2, so every figure below comes from
synthetic fixtures. **No pixel statistic in this document describes the Trishuli
corridor.**

---

## 1. What was already in place (M2), reused not rebuilt

`src/floodmap/preprocessing/` already provided: required-band validation against
named bands, reflectance scale/offset application from configuration,
nodata/GDAL validity masks, reprojection onto the canonical grid through the
**shared** `reprojection.py` warp, per-raster-kind resampling methods, artifact
writing with provenance, and the `invalid_pixel_policy: mask` rule (interpolation
is refused, not offered).

The S2 quality mask existed but was values-based only: `band_name` +
`valid_values`. That can express "keep these codes" but not *why* a pixel was
dropped, so cloud, cirrus, shadow and no-data collapsed into one count.

## 2. What M6.2 added

### 2.1 SCL class semantics — `src/floodmap/preprocessing/s2_optical.py`

* `SCL_CLASSES`: the published Sentinel-2 L2A Scene Classification Layer table
  (codes 0–11), each entry carrying its category and whether it is a usable
  surface observation. Water (6) **is** an observation — the flood question is
  which water, not whether water is visible.
* `classify_scl()`: per-category counts. A code outside 0–11 is counted as
  `unexpected` and reported; it never enters the valid mask, so a change in the
  provider's encoding shows up as an anomaly instead of silently widening the
  mask.
* `observation_mask()`: usable-pixel mask derived from the table.
* The table is cited (`SCL_REFERENCE`) and is to be checked against the delivered
  product's own metadata; an AI transcription of a specification is not
  validation (`AGENTS.md` §11).

### 2.2 The three states, kept apart — `aoi_statistics()`

| State | Meaning | Counted as |
|---|---|---|
| **missing data** | No observation exists: outside the imaged extent, raster nodata, or SCL `no_data`/`saturated` | `missing_*` |
| **masked** | An observation exists and is deliberately rejected: cloud, thin cirrus, cloud shadow, snow/ice | `masked_*` |
| **valid observation** | Usable as evidence | `valid_observations` |

* Every fraction is relative to **pixels inside the AOI**, never to the raster —
  a granule-wide denominator would be dominated by land nobody asked about.
* `fully_accounted_for` asserts the three states plus `unexpected` sum to the AOI
  pixel count, so a silent leak in the accounting is a test failure rather than a
  plausible-looking percentage.
* An empty AOI raises rather than returning zeros: "the mask selects nothing" is
  a geometry/grid error, not a data-availability finding.
* `BandAvailability` reports required vs present vs **missing** band names
  explicitly, so a missing band cannot masquerade as a cloudy one.

### 2.3 Pipeline wiring — `preprocess_sentinel2_pair`

Enabled by configuration (`sentinel2.cloud_mask_source: scl`), which is
**deliberately left unset** in `configs/preprocessing.yaml`: choosing a mask
source is a production decision. When it is set:

* the SCL band is located by description and read; a band whose values are not
  integral **fails** rather than being truncated into classes;
* the class mask is applied to the validity mask before the warp, as the
  values-based path does;
* the SCL is warped to the canonical grid by the **shared**
  `reproject_categorical()` — nearest-neighbour only, and it *refuses* an
  averaging method, because bilinear across a 0/2 boundary invents class 1. The
  method comes from `target_grid.resampling.categorical_label`, so an operator who
  changes it must say so. (A local warp was written first and removed: the M5
  structural guard exists precisely to stop the M2 pipeline growing its own warp,
  and it caught the duplication.)
* AOI statistics are computed on the analysis grid over the AOI, and
  `aoi_cloud_percent` stops being `unknown` — it is only ever upgraded when a
  mask actually exists to measure it from;
* a per-scene machine-readable report is written to
  `<output_dir>/sentinel2/{before|after}_{scene_id}.optical-validation.json` and
  embedded in the artifact's `quality` block.

Report contents: `observation_states`, `scl` (counts + reference),
`bands`, `reflectance_scaling`, `resampling` (including the categorical method and
its warp provenance), `masking`, and `limitations`.

## 3. Implemented and tested vs planned

| Item | State |
|---|---|
| SCL band discovery + required-band verification | **Implemented**, tested (`tests/test_preprocessing_m2.py`, `tests/test_s2_optical_validation.py`) |
| SCL-based cloud / cirrus / cloud-shadow / invalid masking | **Implemented**, tested on synthetic SCL |
| Nearest-neighbour SCL resampling, averaging refused | **Implemented** via shared `reproject_categorical`; method configurable |
| AOI valid-pixel, cloud and shadow fractions | **Implemented**, tested |
| Raster coverage and per-band availability statistics | **Implemented**, tested |
| Machine-readable report distinguishing missing / masked / valid | **Implemented**, tested (JSON round-trip) |
| Non-integral SCL band refused | **Implemented**, tested |
| Continuous reflectance resampling method | **Configured** (`sentinel2.resampling`); unchanged from M2 |
| Reflectance scale/offset | **Applied from configuration**; **not** auto-derived from product metadata — *planned* |
| Sun-angle / DEM-based topographic correction | **Not implemented** (not in M6.2 scope) |
| Real-product band names, SCL presence, scaling factors | **Unverified** — requires a delivered product |
| AOI cloud/valid-pixel statistics on real imagery | **Unverified** — requires pixels |
| Mosaicking several granules into one AOI coverage | **Not implemented**; §4 of `docs/m6.2-catalogue-requery.md` shows it is required for this corridor |

## 5. What is still required before any optical claim

1. **A product whose granule actually covers the corridor** — or a mosaic of at
   least two granules (45RUL + 45RUM). Under the current single-scene gate, no
   discovered Sentinel-2 granule qualifies
   (`docs/m6.2-catalogue-requery.md` §4).
2. **The `download.enabled` decision, once AOI provenance is approved.** Optical
   metrics cannot be produced from metadata.
3. **Verification of the SCL table and the band set against the delivered
   product's metadata**, not against this document.
4. **A decision on the acceptable valid-pixel fraction**, so "usable" is a stated
   threshold rather than an impression.
