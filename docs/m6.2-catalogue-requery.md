# M6.2 — Live catalogue requery for the 26 August 2026 Trishuli flood

**Scope.** Metadata discovery only, through the project's own acquisition code.
No product archive was downloaded, no raster was opened, no training was run.

**Question this answers.** For the Trishuli corridor and event date `2026-08-26`,
what does the CDSE catalogue actually hold in the window the project has been
using (15 days before, 3 days after), and are the four previously reported
candidate products retrievable and usable?

**AOI.** `configs/aoi/trishuli-corridor-UNVERIFIED.geojson`
(`trishuli-corridor-UNVERIFIED-9035eeee`), **UNVERIFIED provenance**, hash-pinned.
It is configured provisionally for metadata-only work; no download was possible
or attempted against it (`AreaOfInterest.authorises_download` is `false`).

---

## 1. How the query was run

```
# The AOI polygon cannot be sent in full: see §2. This is the run that worked.
.venv/bin/python scripts/acquire.py --query-envelope-prefilter \
    --before-days 15 --after-days 3 \
    --manifest artifacts/m6_2/catalogue_requery_20260826/manifest.json
# exit 0

# The default (no pre-filter). Preserved as the evidence for §2.
.venv/bin/python scripts/acquire.py \
    --before-days 15 --after-days 3 \
    --manifest artifacts/m6_2/catalogue_requery_20260826/blocker_no_prefilter_manifest.json
# exit 2
```

Search window actually used: `2026-08-11T00:00Z → 2026-08-30T00:00Z`, i.e.
15 days before and 3 days after the event, with the **event day itself excluded**
(the event time of day is unknown, so a same-day scene cannot be classified as
pre- or post-event). Both the window and that exclusion are recorded in the
manifest's `temporal_plans`.

Nothing was downloaded: both manifests record
`download_status: download_not_attempted` for all four selected/considered
products, and no `data/raw` bytes exist (checked).

## 2. Blocker found and how it was handled: the query URL is too long

Sent in full, the corridor polygon produces an OData URL of **41,135 characters**
(1,514 distinct vertices / 1,515 ring points). The endpoint does not answer it —
the connection is closed without a response, and the transport's bounded retry
budget (`max_attempts: 3`, the code default) is exhausted, producing
`discovery_failed` with `error_type: ProviderTimeout`. No attempt count or retry
log is stored in the manifest, so the three attempts are the configured budget
rather than a measured trace. Bracketed against the same endpoint with the same
sensor and window:

| Query geometry | URL length | Live outcome |
|---|---|---|
| corridor polygon, 1,515 ring points (1,514 distinct) | 41,135 | connection closed, `discovery_failed` |
| corridor, every 16th vertex, 96 ring points (95 distinct) | 3,151 | `discovery_success`, 5 scenes |
| corridor, every 63rd vertex, 26 ring points (25 distinct) | 1,275 | `discovery_success`, 5 scenes |
| AOI bounding envelope, 5 points | 715 | `discovery_success`, 5 scenes |

So the endpoint accepts a few kilobytes and refuses ~41 kB. The failure is a
property of the transmission format, not of the data or the AOI.

**Every length in that table is reproducible without a network call.** The
41,135 and 715 figures are readable straight out of the two preserved manifests
(`len(discoveries["sentinel-1"].executed_url)`); all four re-derive from the
project's own URL builder through `--dry-run`, which builds the query URL and
refuses to fetch:

```bash
# 41,135 (config AOI, full polygon)
.venv/bin/python scripts/acquire.py --dry-run --before-days 15 --after-days 3 \
    --manifest /tmp/dry_full.json

# 715 (bounding envelope of the same AOI)
.venv/bin/python scripts/acquire.py --dry-run --query-envelope-prefilter \
    --before-days 15 --after-days 3 --manifest /tmp/dry_full_env.json

# 3,151 and 1,275: subsample the ring every 16th / 63rd vertex, closing it
.venv/bin/python - <<'PY'
import json
from pathlib import Path
doc = json.loads(Path("configs/aoi/trishuli-corridor-UNVERIFIED.geojson").read_text())
ring = doc["features"][0]["geometry"]["coordinates"][0]
for step, label in ((16, 96), (63, 26)):
    sub = ring[::step]
    if sub[-1] != ring[0]:
        sub.append(ring[0])  # a ring must be closed; the model refuses an open one
    Path(f"/tmp/aoi_{label}.geojson").write_text(
        json.dumps({"type": "Polygon", "coordinates": [sub]})
    )
PY
# then, for each file:
#   scripts/acquire.py --dry-run --aoi-geojson /tmp/aoi_96.geojson --aoi-id s96 \
#       --before-days 15 --after-days 3 --manifest /tmp/dry_s96.json
# and read len(discoveries["sentinel-1"].executed_url)
```

The subsample rule is stated because it *changes the length*: the URL carries the
ring as WKT at ~18 characters per vertex pair. An earlier version of this table
quoted 1,251 and 708 for the two smallest cases — those came from an ad-hoc
subsample whose rule was not written down, and they are superseded by the values
above, which re-derive exactly.

**Handling.** `--query-envelope-prefilter` sends the AOI's bounding envelope as
the *catalogue spatial filter* while the AOI polygon remains the geometry that
coverage is measured against. The envelope is a strict superset of the corridor,
so the filter cannot exclude a candidate the corridor would have matched; it only
widens the candidate list, which the 0.9 coverage gate then trims. The
substitution, its reason and both geometries are recorded in the manifest
(`query_prefilter`, `requests[].aoi_wkt` = pre-filter,
`selections[].selection_policy.aoi_wkt` = AOI) and in the manifest limitations.

**No gate was bypassed.** Coverage is still measured against the corridor
polygon; the download gate still refuses (`download.enabled: false` *and*
`provenance_status: unverified`).

**Defect fixed while doing this.** A failed Sentinel-1 query was being reported
as *"no Sentinel-1 before/after pair shares a verified relative orbit"* — a data
finding the run had not established. A failed discovery is now reported as a
failed query, and the failing run still writes its manifest before the error
propagates, so the evidence survives the non-zero exit.

## 4. Sentinel-2 — discovery succeeds, and no single granule can meet the gate

Discovery: `discovery_success`, **60 candidates**, 1 page, no truncation.
Composition: **30 L2A + 30 L1C**, tiles `45RUL` (20), `45RUM` (20), `45RTM` (10),
`45RTL` (10). Scene-level cloud cover is reported for all 60 (min 5.21 %,
max 99.90 %, mean 61.4 %) — but cloud never became the deciding factor, because
every candidate failed the coverage gate first.

Selection outcome: **`no_usable_scene`, `is_usable: false`** — the before-side had
no eligible candidate. All 60 candidates were rejected, with recorded reasons:

| Side | Reason | Count |
|---|---|---|
| before | `footprint_does_not_intersect_aoi` | 24 |
| before | `footprint_coverage_below_minimum` | 24 |
| after | `footprint_does_not_intersect_aoi` | 6 |
| after | `footprint_coverage_below_minimum` | 6 |

**The finding.** No single discovered granule comes close to covering the
corridor:

* **maximum single-granule coverage of the corridor: 78.05 %**
  (`S2C_MSIL2A_20260822T045651_N0512_R119_T45RUM_20260822T095910.SAFE`; the
  other `45RUM` granules share that footprint) — below the configured 0.9 for
  **all 60** candidates;
* the corridor is **~66 km long** and runs north-east across the
  `45RUL`/`45RUM` tile boundary (measured: perimeter 133.85 km of a polygon
  declared as a 1 km buffer around a centreline gives a centreline length of
  65.9 km; the area-based estimate is 65.1 km. The corridor's own bounding box is
  32.4 × 49.4 km, a 59.1 km diagonal). A single Sentinel-2 granule's *catalogue
  footprint* at this latitude spans 75–112 km east–west and 61–112 km
  north–south (median ≈ 105 × 112 km over the 60 candidates), but its imaged
  quad does not align with the corridor's diagonal;
* **the union of the discovered granules covers 100.0 % of the corridor**, and a
  greedy search finds a **two-granule** set (`45RUL` + `45RUM`, same date) that
  already covers it — so a mosaic would satisfy the coverage requirement. Both
  figures are measured from the manifest's own footprints by the snippet in §5;
  they are a one-off geometric measurement, **not** a mosaic capability in the
  pipeline (see §6 and `docs/m6.2-sentinel2-optical-validation.md` §3).

This is a policy finding, not a bug in the gate: the gate is doing exactly what
it was built to do (refuse a scene that clips the study area), but
`minimum_aoi_coverage: 0.9` was set for a *single scene* and this corridor cannot
be covered by a single optical granule. Changing the threshold, or allowing a
mosaic, is a scientific decision that belongs to the operator. It was **not**
changed.

**Comparison with the historical report — this is the substantive correction.**

| Historical identifier | Fresh result |
|---|---|
| `S2A_MSIL2A_20260811T045241_N0512_R076_T45RUL_20260811T100012.SAFE` | present in the catalogue, **rejected: `footprint_does_not_intersect_aoi`, measured coverage 0.0000 %** |
| `S2B_MSIL2A_20260827T045659_N0512_R119_T45RUL_20260827T084453.SAFE` | present in the catalogue, **rejected: `footprint_coverage_below_minimum`, measured coverage 39.8884 %** (scene cloud 54.29 %) |

Both historical Sentinel-2 "candidates" therefore exist but are **not usable** for
this corridor: the pre-event granule does not intersect the corridor at all, and
the post-event granule leaves ~60 % of it outside the image. A pre/post optical
comparison built on them would have covered roughly 0 % and 40 % of the study
area respectively — which is precisely the "flood extent bounded by the image
edge" failure the coverage gate exists to prevent. The historical report did not
claim otherwise, but it also could not show this; it can now be shown, quantified,
and reproduced.

`configs/data.yaml → sentinel2.processing_level_preference: L2A` was in force.
Both levels were discovered; the level gate never decided anything because the
coverage gate rejected the candidates first. Tile compatibility and mixed-level
rankings are therefore **not exercised by this run** — they are covered by tests,
not by this evidence.

## 5. Reproducing this

Requirements: network access to `catalogue.dataspace.copernicus.eu` (anonymous
access was sufficient; credentials are read from environment variable *names*
only and none appear in any artifact) and the repository's `.venv`.

1. Run the two commands in §1. The envelope pre-filter is required; without it
   the Sentinel-1 query fails as in §2.
2. Compare the output manifest against the tables in §3 and §4. Every number
   above comes from `manifest.json`; the rejection reasons and measured coverage
   fractions are in `selections[*].rejected_candidates` and
   `selections[*].coverage`.
3. The window is not hard-coded: it comes from `--before-days/--after-days` and
   is written into the manifest, because the config ships the windows as `null`.
4. The coverage numbers in §3 and §4 are re-derived from the manifest alone — no
   network — by this snippet, which measures in the same local planar frame as
   `src/floodmap/acquisition/coverage.py` (longitude scaled by `cos(latitude)`
   about the origin, ratio of planar areas):

```bash
.venv/bin/python - <<'PY'
import json, math
from shapely import affinity, wkt
from shapely.geometry import shape
from shapely.ops import unary_union

m = json.load(open("artifacts/m6_2/catalogue_requery_20260826/manifest.json"))
aoi = wkt.loads(m["selections"]["sentinel-2"]["selection_policy"]["aoi_wkt"])
lat = aoi.centroid.y
local = lambda g: affinity.scale(g, xfact=math.cos(math.radians(lat)), yfact=1.0, origin=(0.0, 0.0))
aoi_local = local(aoi)
polys = [local(shape({"type": p["footprint"]["type"], "coordinates": p["footprint"]["coordinates"]}))
         for p in m["discoveries"]["sentinel-2"]["scenes"] if p.get("footprint")]
print("granules:", len(polys))
print("max single granule: %.4f%%" % (100 * max(aoi_local.intersection(p).area for p in polys) / aoi_local.area))
print("union of all: %.4f%%" % (100 * aoi_local.intersection(unary_union(polys)).area / aoi_local.area))
PY
```

```
granules: 60
max single granule: 78.0466%
union of all: 100.0000%
```

Because it reads `selections["sentinel-2"].selection_policy.aoi_wkt`, it measures
against the **corridor polygon**, not the envelope used for the query. These are
the first two figures in §4 re-derived independently of the code that produced
the manifest; the greedy two-granule set was computed separately in the same
frame.

## 6. Limitations of this requery

* **AOI provenance is UNVERIFIED.** Every coverage number above is relative to a
  geometry whose producer and buffering are unrecorded
  (`docs/dataset-registry.md` §1.6.3). If the corridor is replaced, these numbers
  must be recomputed.
* **The query geometry was the envelope, not the polygon** (§2). The candidate
  *set* is therefore a superset: "the catalogue holds nothing usable" would still
  be a valid conclusion, "these 60 are all that exists" would not be.
* **Nothing was downloaded**, so online/offline status, archive integrity and
  actual pixel usability are all untested.
* **Cloud is scene-level metadata** (60/60 reported) and says nothing about cloud
  over the corridor; AOI-level cloud and valid-pixel fractions require the pixels.
* **One page, no truncation** (`truncated: false`, 200-result cap not reached),
  but the provider's `$top`/`$skip` behaviour is unverified for larger result sets.
* **Sentinel-1 pair quality is not assessed here**: the pair is geometrically
  compatible, not radiometrically compared.
* **The 100 % union figure is a property of the footprints, not of any product.**
  It compares catalogue footprint polygons against the AOI. It does not mean the
  granules carry usable pixels there, and nothing in the pipeline mosaics them
  today (§5 snippet; `docs/m6.2-sentinel2-optical-validation.md` §3).
