# M6.5 — Readiness gate and execution-status reconciliation

**Verdict: M6.5 is complete for its stated scope. Its outputs are available for
explicitly labelled scenario analysis. Operational use is BLOCKED.**

Those are three separate findings and this document does not merge them. The
gate that produces them is `src/floodmap/dashboard/readiness.py`; the tests are
`tests/test_m65_readiness_gate.py`; the runner is
`scripts/m65_readiness_gate.py`.

---

## 1. Why a gate, and not a status flag

`src/floodmap/dashboard/workflow.py` answers *did the stage run?* and answers it
from the presence of an output file (`_output_stage_status`, line 250). That is
correct for a pipeline view and insufficient for authorising anything. A stage
can have run, produced internally consistent artifacts, and passed its tests,
and still be unfit for operational use — because fitness depends on evidence
that lives outside the stage: whether absolute geolocation was ever validated,
how much of the AOI was observed, and whether the AOI boundary has established
provenance.

So the gate reports three verdicts and refuses to collapse them:

| Use class | Question | Current verdict |
|---|---|---|
| `stage_completion` | Is M6.5 complete for its **own stated scope**? | `complete_for_stated_scope` |
| `research_scenario_use` | May outputs be used for **labelled** scenario work? | `permitted_with_labels` |
| `operational_use` | Is downstream **operational** use authorised? | **`blocked`** (5 open blockers) |

`authorise_use()` **raises** `ReadinessGateError` rather than returning a value a
caller could ignore. There is no flag, config key or argument that grants
operational authorisation — `--require-operational` exists only to make the
blocked state *testable*, and exits 3.

## 2. What M6.5 implements, and what its outputs represent

M6.5 consumes the M6.4 candidate-exposure artifacts and answers the Track B
question *who may be cut off* — **as a scenario, under a closure rule it states
explicitly**.

It builds the pre-event road graph, applies a hypothetical closure rule to roads
M6.4 measured as candidate-intersecting, compares connected components and
settlement-to-hub routes against the untouched baseline, and reports threshold
sensitivity and coverage uncertainty.

What the outputs are **not**:

- not confirmed flood extent — M6.3 candidates are rule-based Sentinel-1 RTC
  dual-polarisation γ⁰ darkening evidence;
- not confirmed infrastructure damage — a flood mask intersecting a road is
  spatial exposure, not physical destruction (`AGENTS.md` §8);
- not observed road impassability — closure is a stated assumption;
- not validated real-world responder routes — shortest paths by length on a
  graph that ignores capacity, surface, gradient, seasonal passability, bridge
  load limits and landslide risk.

A settlement reported `SCENARIO_UNREACHABLE` *would* lose its modelled road route
to that hub group *if* candidate-intersecting roads were impassable. That is a
modelled consequence of a stated rule, not a finding that anybody is cut off.

## 3. Execution-status reconciliation

### 3.1 The stale blocker

`candidate_disruption_blocker.json` records a **real** refusal:

| Field | Value |
|---|---|
| `status` | `blocked` |
| `generated_at` | `2026-10-17T09:24:48.123371+00:00` |
| `reason` | required M6.4 artifacts not present on disk |

The stage has since run. The summary declares:

| Field | Value |
|---|---|
| `stage` | `m6.5-candidate-network-disruption-0.1.0` |
| `status` | `hypothetical_closure_scenario` |
| `generated_at` | `2026-10-18T07:15:13.281034+00:00` |
| `hub_reachability.assessed` | `true` |

The summary is **22 hours newer** than the blocker, so the blocker is superseded
history.

**The blocker is not rewritten.** `AGENTS.md` §22 wants the chain of evidence
intact, and a blocker report is the right artifact to keep: it is a photograph of
a moment when the stage correctly refused to invent data. Verified
byte-for-byte: `sha256 d77c7571…0a68` before and after running the gate, and a
test (`test_stale_blocker_is_not_rewritten`) pins it.

Instead the gate writes a **separate** reconciliation record,
`candidate_disruption_execution_record.json`, naming which artifact is current
and why. It is git-ignored under `.gitignore:25` (`artifacts/*`), per §15.

### 3.2 Execution evidence is content, not file presence

`reconcile_execution()` accepts a summary as execution evidence only when it

1. parses as a JSON object,
2. carries the `m6.5-candidate-network-disruption` stage tag, and
3. declares `status == "hypothetical_closure_scenario"`.

Anything else is `indeterminate` — and `indeterminate` is **never** permission
(`test_indeterminate_is_never_treated_as_permission`). An empty file, a `[1,2,3]`
array, an M6.4 summary misplaced into the M6.5 directory, or an unparseable
timestamp all fail to authorise.

Verdicts: `executed_blocker_stale` (current state), `executed_no_blocker`,
`blocked_current`, `not_executed`, `indeterminate`.

## 6. Reproducibility — what was and was not checked

**Performed:**

- the stage executed successfully and recorded provenance;
- internal consistency of summary, provenance and GeoJSON (§4 table);
- AOI source checksum recomputed and matched;
- full test suite passed in the documented environment.

**Not performed:**

- **no independent clean-run reproduction.** The artifacts were not regenerated
  from scratch in a clean environment and compared. Re-running M6.5 was
  deliberately avoided: it would overwrite production artifacts, which Phase 3
  forbids.
- **no per-output-file checksum manifest exists.** The M6.5 provenance carries
  `aoi_source_sha256` only. There is no recorded digest for
  `_pieces.geojson`, `_routes.geojson`, `_settlements.geojson` or `_summary.json`
  to compare current files against. Their integrity was checked by *internal
  consistency*, which is weaker.

The gate encodes this distinction rather than papering over it: the
`reproducibility` limitation is `not_independently_verified`, and
`clean_run_reproduced` is a **parameter defaulting to `False`** that no code path
infers. `test_clean_run_reproducibility_is_never_inferred` pins that a successful
execution does not flip it.

## 7. The three continuing operational blockers

### 7.1 Absolute geolocation accuracy — UNRESOLVED

| M6.20 criterion | Threshold | Measured | Status |
|---|---|---:|---|
| Geolocation shift vs delivered RTC | ≤ 2 px | **4.472 px** | FAIL |
| Correlation vs delivered RTC | ≥ 0.5 | **0.237917** | FAIL |

Thresholds preregistered at `configs/rtc_reprocessing.yaml:315-316`; measurements
at `docs/m6.21-geolocation-investigation.md:9,77`.

M6.21 established a measured *cause* — ~92 % of the shift is the vertical-datum
convention difference between the probe and the delivered product. That is a
genuine finding and it **does not establish validated absolute geolocation**.
M6.21 explicitly does not re-score these criteria, and records the delivered
Catalyst RTC as **NO-GO** as an absolute-geolocation reference at ≤2 px
(`docs/m6.21-geolocation-investigation.md:361`). Reaching the delivered grid
would require deliberately geolocating with a ~40 m height error — a regression,
not a fix.

**To close:** a pre-registered replacement criterion against a datum-matched
reference, measured and passed.

### 7.2 Partial AOI coverage — PARTIAL

The delivered RTC window covers **63.3719 %** of the adopted AOI
(130.641632 km²); **36.6281 %** (75.509019 km²) is unobserved. `delivered +
unobserved = extent` exactly.

Unobserved area and the infrastructure in it **must never** be classified as dry,
safe, unaffected, flood-free or connected. Absence of observation is not a
negative finding. Of 581 settlements, M6.4 classified 380 `OUTSIDE_CANDIDATE_GRID`
and 169 `UNOBSERVED` — 94.5 % carry no usable observation, and exactly **1** is
`CANDIDATE_INTERSECTING`.

**To close:** process both dates identically over the full AOI and re-measure
with `floodmap.hydrology.coverage`. Requires separate authorisation.

### 7.3 AOI provenance — UNVERIFIED

The HydroRIVERS-derived corridor
`trishuli-corridor-hydrorivers-v10-m615-2ae4183f` is a **project-defined
analytical AOI**, not a verified official competition boundary. Adopting the
geometry (M6.15) did not establish its origin and does not authorise retrieval;
`AreaOfInterest.authorises_download` is `false`
(`src/floodmap/acquisition/aoi.py`). Every count is relative to an extent whose
provenance is not established.

**To close:** establish and record the boundary's origin, or substitute a
boundary whose provenance is verifiable.

### 7.4 Also blocking, by design

| Limitation | State |
|---|---|
| `evidence_semantics` | `stated_scenario` — candidate exposure and hypothetical closure are unconditionally non-operational |
| `reproducibility` | `not_independently_verified` — §6 |

`test_no_combination_of_evidence_authorises_operations` proves the point: even
with hypothetical clean geolocation, 100 % coverage **and** a claimed clean run,
operational use stays blocked. Provenance and evidence semantics do not yield to
better numbers elsewhere.

## 8. Research readiness vs operational readiness

**Research / scenario use is permitted** — the stage's own contract allows
explicitly labelled candidate-exposure and scenario connectivity analysis, with
threshold sensitivity and coverage uncertainty reported alongside every number.

It is permitted **only** carrying these five labels, which
`GateOutcome.required_labels` supplies and which a blocked outcome does **not**
hand out:

1. SAR-change candidate exposure — not confirmed flood extent or infrastructure damage.
2. Road closures and connectivity changes are hypothetical scenarios under a stated closure rule — not observed impassability and not validated responder routes.
3. Partial observation coverage: 36.6281 % of the AOI is unobserved. Unobserved area is not dry, safe, unaffected or connected.
4. AOI provenance is UNVERIFIED: a project-defined analytical corridor, not a verified official competition boundary.
5. Absolute geolocation is not validated: the preregistered acceptance criteria failed.

**Operational use is blocked** on all five limitations in §7.

### 8.1 The claim screen

`screen_claim(text)` guards the §8 vocabulary boundary. A dashboard, report or
downstream consumer runs its own strings through it and refuses to render a
sentence that promotes candidate exposure to confirmed damage, a scenario to
confirmed accessibility, or missing coverage to a negative finding.

Flagged: `destroyed`, `structurally failed`, `confirmed flood`, `confirmed
damage`, `observed flooding`, `impassable`, `cut off`, `isolated`,
`inaccessible`, `flood-free`, `unaffected`, `undamaged` — each mapped to the
phrasing §8 permits instead.

Not flagged: the hedged vocabulary (`potentially cut off`, `potentially
inaccessible`), the `SCENARIO_*` status names, and **negated** claims — "not
confirmed flood extent" is the phrasing the project requires, so flagging it
would make the screen unusable and invite bypassing.

The gate's own labels and limitation text pass its own screen
(`test_the_gates_own_labels_pass_its_own_screen`), and the runner refuses to
write a record whose text fails it.

**Known limits, stated plainly.** This is a lexical heuristic, not semantic
analysis: negation is detected within a 12-word window bounded by sentence
breaks, so a compound sentence that denies one claim and asserts another can slip
through, and a double negative reads as permitted. It catches careless phrasing.
It is not a proof of correct phrasing, and passing it does not make a claim true.

## 9. Running it

```bash
.venv/bin/python scripts/m65_readiness_gate.py            # reconcile + write record
.venv/bin/python scripts/m65_readiness_gate.py --check    # report only, no write
.venv/bin/python scripts/m65_readiness_gate.py --require-operational   # exits 3
```

| Exit | Meaning |
|---:|---|
| 0 | Gate built; completion and research use resolved; operational blocked (expected) |
| 1 | Unusable path argument, or the gate's own text failed its claim screen |
| 2 | M6.5 execution not verified (not executed, currently blocked, or indeterminate) |
| 3 | `--require-operational` and operational use is blocked |

The script downloads nothing, trains nothing, runs no science, and writes exactly
one file: the execution record, inside the git-ignored `artifacts/` tree.

## 10. Follow-up work

| # | Blocker | Evidence required to close |
|---|---|---|
| 1 | Absolute geolocation | Pre-registered replacement criterion against a datum-matched reference, measured and passed. §7.1 |
| 2 | AOI coverage | Full-AOI processing of both dates, identically, re-measured. Needs separate authorisation. §7.2 |
| 3 | AOI provenance | Established, recorded origin for the corridor boundary — or a boundary whose provenance is verifiable. §7.3 |
| 4 | Clean-run reproducibility | From-scratch re-execution in a clean environment, into a scratch directory, compared against current artifacts. §6 |
| 5 | Checksum manifest | Per-output-file digests recorded in M6.5 provenance, so future integrity checks are cryptographic rather than consistency-based. §6 |

Items 4 and 5 are in-scope engineering. Items 1–3 require decisions and
authorisations that are not code changes.

Separately: the `road` closure unit closes a whole OSM way on 10 m of candidate
intersection, which overstates disruption on a corridor whose trunk road is tens
of kilometres long. Whether any reported settlement verdict should instead use
`piece` resolution against the real candidate raster is a scientific judgement,
not a code change. The code supports both.
