# M6.11 — AOI Adoption Review and Downstream Reconciliation Plan

**Type:** read-only review. No geometry, configuration, artifact or gate was modified.
**Date:** 2026-10-17
**Scope:** review the M6.10 HydroRIVERS corridor for adoption readiness, plan downstream
reconciliation, and position a FalkorDB design stage (M6.12).

---

## 0. Executive decision

```text
NO-GO — adoption or acquisition prerequisites are not satisfied
```

The geometry is sound. The *justification chain for its downstream extent is not*, and the
documented adoption procedure is incomplete. Specifically:

1. **The downstream terminus is circular.** It is bounded by a raster window that is the
   **old UNVERIFIED AOI's own envelope** (measured below: padded by 18–469 m). M6.9 §3.1 and
   §12 explicitly **rejected** that window as a constraint — "circular evidence… it cannot
   corroborate that polygon's extent, and it must not be treated as a design constraint on the
   replacement" — and M6.9 §9's "Do not" list forbade clipping to its bbox. M6.10 used it
   anyway, with a stated rationale but **without recording that it reverses M6.9**. The new
   corridor's downstream tip consequently lands ~101 m from the old polygon's southernmost
   latitude. This is not a human preference; it is an undisclosed dependency on the artifact
   being replaced, and it must be disclosed or re-derived *before* an operator can take an
   informed §8.2 decision.
2. **Two open operator ratifications** remain by the project's own record (buffer distance,
   extent policy) — these are genuine human decisions.
3. **The documented three-key edit is defective.** Followed literally it would leave
   `configs/data.yaml` internally inconsistent and carrying five `provenance_gaps` strings that
   describe a file no longer configured.
4. **Governance records are still absent**: no HydroRIVERS approval record (M6.9 §8.6), no
   named operator (§8.7).

Acquisition is independently NO-GO: `provenance_status` must stay `unverified` by the project's
own rule, and M6.9 §8.5–8.8 are unresolved.

**What this review does not say:** it does not say the corridor is wrong, nor that it should be
discarded. It is a better artifact than what it replaces on every axis except one, and that one
axis is fixable without rebuilding the geometry.

### 1.4 The adoption change — what it is, and what it actually requires

The handoff (and `configs/aoi/trishuli-corridor-hydrorivers-v10.yaml:46`) cites
"M6.10 §6.3". **There is no §6.3.** M6.10 §6 is "Files changed and checks run". The content is

The documented diff, verbatim:

```diff

-  geojson_path: "configs/aoi/trishuli-corridor-UNVERIFIED.geojson"
-  sha256: "9035eeee025f311be7f16af1d23737a46caee20eb0b2a8dfa144d111b9362610"

+  sha256: "941a4079d3f317e260a91560eaebdd019ab5cf59c87f82e8e6165c7b0564b586"
```

#### What each key does

| Key | Function | Evidence required before changing it |
|---|---|---|
| `geojson_path` | The only pointer the loader follows to read geometry (`acquisition/config.py:389-401`). Changing it changes the study extent that **every** downstream number inherits. | Ratification of the **extent policy** — main-stem-only, coverage-bounded (M6.10 §5.1 item 1; M6.9 §8.2, §8.3). Plus, per this review, resolution of the circular terminus (§2.2 below). |
| `sha256` | Pinned bytes; the loader **refuses to load** on mismatch rather than silently analysing a different extent. It is a drift/tamper guard, **not** an authorisation. | None beyond the digest already being reproducible — M6.10 §5.2 "no new hashes". Verified below: `--check` → MATCH. |
| `aoi_id` | The stable label stamped into every artifact, **and a path component**: `scripts/impact.py:243` builds `artifacts/impact/<aoi_id>`. Changing it re-keys artifact discovery. | Same extent ratification; M6.9 §9 step 8 requires it change **atomically** with path, sha256, status and gaps. |
| `provenance_status` | **The actual gate.** `AreaOfInterest.authorises_download` returns True **only** for `VERIFIED` (`acquisition/aoi.py:326-337`). **(a) It addresses one block; the file has two.** These keys exist in both the top-level `aoi`

## Phase 2 — Adoption readiness

### 2.1 The 1,000 m buffer

**Not sufficiently justified to adopt without ratification. A human decision is required.**

M6.9 §5.1 does re-derive it, and the derivation is reasonable: HydroRIVERS is a 15 arc-second
product, which at 28.0° N is 460.7 m N–S and 409.5 m E–W, so 1,000 m is ≈ 2.2 × one source cell
and the corridor contains the channel belt under any plausible positional offset of a coarse
centreline. M6.9 also states the counter-argument itself — every extra kilometre of width
inflates every exposure count with features merely *near* the river.

Three things stop this being adoptable as-is:

- **M6.9 classifies its own rationale as an assumption**, not a measurement (§11.2).
- **M6.10 does not actually rely on that derivation.** It restates the choice as *"matches the
  M6.2–M6.5 corridor width, so the replacement is comparable"* (§3.2) and concedes it is
  *"carried over for comparability and is unsupported by any operator decision"* (§5.1 item 2).
  Comparability with an unverified predecessor is not a scientific justification.
- **The mandatory sensitivity set is incomplete.** `{500, 1000, 2000}` m was required; 2,000 m
  **failed** and is recorded as `no_fully_covered_corridor` — the buffered geometry is a 3-part
  MultiPolygon (1,315,257.6 m² outside the largest part) and the AOI contract accepts a single
  Polygon. The refusal is correctly recorded rather than silently reduced to the largest part,
  which is good practice. But M6.9 §5.1 required per-buffer coverage **and** M6.4-style exposure
  counts and M6.5-style settlement counts for all three widths. None of those exist for any
  width, because M6.4/M6.5 produced no real numbers at all (§3.1). **Buffer sensitivity has
  therefore never been evaluated against the quantities it was supposed to test.**

The honest position: 1,000 m has a defensible floor argument and no ratified owner, and its
result-sensitivity is unmeasured. It needs a named decision in writing.

### 2.2 The downstream endpoint at 64.2 km — **the blocking technical finding**

**Not acceptable as currently justified.** Not because 64 km is wrong, but because the boundary
that produced it is circular.

M6.10 frames the terminus as an instrument limit: *"the corridor stops where the delivered
products stop observing, 64.2 km from the border"* (§7.2). The mechanism is
`terminus_rule: coverage_bounded` — walk `NEXT_DOWN` and keep the last reach whose fully
buffered corridor is `within` the intersection of the delivered product footprints
(`hydrorivers.py:677-696`). Without such a rule the AOI would be a continental river: the walk
runs ~1,380 km to the Bay of Bengal.

The problem is **what that footprint is**. Measured in EPSG:32645:

| Raster-rectangle edge vs **old UNVERIFIED AOI** envelope | Pad |
|---|---|
| west | 50.1 m |
| south | 436.7 m |
| east | 17.7 m |
| north | 468.9 m |

The delivered RTC window **is the old AOI's bounding box**, padded by 18–469 m and snapped to
the 10 m grid. `assembly_provenance.json` makes the derivation explicit: it records
`aoi_bounds_4326: [85.05814, 27.843973, 85.387889, 28.287426]` — the old polygon's envelope —
alongside the `window_bounds` that were cut from it.

And the terminus genuinely binds on that edge:

| New AOI edge → raster edge | Distance |
|---|---|
| west | 1,149.3 m |
| **south (downstream)** | **331.8 m** |
| east | 71.1 m |
| north | 865.9 m |

Consequence, stated plainly: the new corridor's downstream tip lies at latitude 27.8430609; the
**old** polygon's southernmost latitude is 27.843973 — a separation of **~101 m**. The
"independent" HydroRIVERS corridor ends, to within about a hundred metres, exactly where the
unverified polygon it replaces ended. It had to: the window it was tested against was that
polygon's envelope.

This directly contradicts M6.9's own governing decisions:

> The raster footprint is *circular evidence*: it was derived from
> `trishuli-corridor-UNVERIFIED.geojson`, the geometry under investigation. It cannot
> corroborate that polygon's extent, and it must not be treated as a design constraint on the
> replacement. — M6.9 §3.1

> `Existing raster footprint as a constraint: REJECTED — it is derived from the old AOI (§3.1)`
> — M6.9 §12

> **Do not** in M6.10: reuse the existing polygon's coordinates, buffer, or termini; reuse its
> hash or id; **clip to its bbox**. — M6.9 §9

M6.10 §2.3 gives a rationale — *"the products are what M6.2–M6.5 actually analysed"* — which is
a coherent argument for comparability. But it **does not record that it reverses M6.9 §3.1 and
§12**, and M6.10 §2.2 asserts only the narrower claim that *"the corridor is not clipped to the
old bounding box"*. Strictly, the polygon was not clipped; but its downstream terminus was
*selected* by containment in that box, which is the same dependency arriving by a different
route. M6.10 §7's limitations present the downstream end purely as an instrument boundary and
never disclose its lineage.

Two further discrepancies in the same mechanism:

- **The 250 m inset was silently dropped.** M6.9 §4.2 and §6.2 step 3 specified containment in
  the common footprint *"inset by an additional 250 m margin"*. The implementation tests bare
  `within()` with no inset. M6.10 does not record the removal, yet its own §3.2 still refers to
  *"the inset that defined it"*. With only 331.8 m of margin at the south edge, a 250 m inset
  would have materially moved the terminus — this is not a cosmetic omission.
- **`downstream_stop_reason: no_downstream_connection` is misleading.** That value means
  `NEXT_DOWN == 0`, i.e. the river's end. It is recorded because `downstream_path()` is called
  with no `stop_at` (`hydrorivers.py:662`), so the *untruncated* ~1,380 km walk's reason is
  stored on the *truncated* selection (`:710`). `terminus_is_river_end: false` carries the true
  meaning. A reader of the provenance file alone would reasonably conclude the corridor ends
  where the river ends. Neither M6.9 nor M6.10 mentions the field, and the test only asserts set
  membership (`test_aoi_hydrorivers_corridor.py:284`).

**None of this makes the geometry invalid.** It makes the *stated justification* for the
downstream extent unsound, and it means an operator asked to ratify §8.2 today would be
ratifying without being told the boundary traces back to the artifact under replacement.

### 2.3 Contract and case-study intent

**Satisfied on intent; a disclosure obligation attaches.**

The challenge requires end-to-end execution from raw satellite data for *judge-selected* areas
and dates. M6.8 established — and nothing since has overturned — that **no organizer-selected
AOI exists in this repository**. A project-defined analytical corridor is therefore the only
available route, and HydroRIVERS is the most defensible source family for one: a persistent,
licensed, citable river-reach network, correctly used here as an **extent definition only**.
`governance.permitted_use` states it explicitly: *"HydroRIVERS is not an inference input: it
contributes no feature, mask or label to the flood model."* `ProductionInput` was deliberately
not widened, so a centreline dataset cannot become an inference input by accident. That is
correct under AGENTS.md §3.

Two obligations follow and are already recorded: the corridor must **never** be presented as the
official AOI, and the buffer must **never** be presented as a flood extent. A hard-coded
corridor also does not satisfy the challenge's judge-selected-AOI requirement; the pipeline must
remain parameterisable by extent, which it currently is only partially (§3.3).

holds "operator" authority — is also still open.

### 2.5 Does full containment establish usable coverage?

**Containment alone does not. For this pair, valid-data coverage is nonetheless established —
by this review, not by M6.10.**

`coverage_fraction: 1.0` is bounding-rectangle containment and would have remained 1.0 with
arbitrarily much nodata inside the corridor. RTC products routinely carry in-bounds nodata from
layover, radar shadow and terrain masking, and this is steep Himalayan terrain — precisely where
that is expected. A per-pixel mask with exactly the right semantics already exists in the repo
(`rtc_valid_mask.tif`, "1=valid pre/post VV+VH change") and is used by neither the coverage check
nor either document.

The measurement in §1.7 closes the question empirically: **1.000000 valid on all four
band/raster combinations inside the new polygon, zero nodata, zero zeros.** So the practical risk
here is nil, while the *methodological* gap is real — the check as written would not have caught
the failure it is supposed to guard. Adoption should carry valid-data coverage as a recorded,
re-measured quantity rather than a fortunate outcome.

### 3.3 The decision that must precede regeneration

The RTC crop is bounded by the old AOI's envelope, and the new AOI fits inside it with 71–1,149 m
to spare on every side (§2.2). Two routes, and they are **not** equivalent:

- **Route 1 — re-cut from the existing full RTC scenes.** The source COGs are 28,197 × 21,106 at
  10 m, far larger than either AOI. Re-cutting a window around the **new** polygon requires no
  new acquisition and no new authorisation, and it removes the old envelope from the lineage of
  every M6.3 raster. It does **not** cure §2.2, because the terminus was already selected under
  the old window.
- **Route 2 — re-derive the terminus against the true scene footprint** (not the delivered crop),
  with the 250 m inset restored as specified. This is what M6.9 §3.1 actually required: *"Any new
  corridor must be checked against the **scene** footprint, never against this crop."* It would
  likely extend the corridor downstream and **change the AOI's bytes, digest and id** — i.e. a new
  geometry milestone, not an adoption.

These must be decided *before* any regeneration, or the work will be done twice. Route 2 is the
scientifically clean answer; Route 1 plus explicit disclosure is the defensible pragmatic one.
**That choice is the operator's, and it is the single highest-value decision outstanding.**

### 3.4 Two integrity defects to fix regardless of adoption

1. **`aoi_id: "trishuli_emsr927_corridor"`** in both legacy acquisition manifests names
   **EMSR927**, which AGENTS.md §3 forbids as a production input. No EMSR927 data is read
   anywhere — it is a label on a superseded artifact, with `sha256: null` and a bbox rather than
   a polygon — but a production acquisition manifest keyed to a forbidden validation source is
   exactly the kind of thing a skeptical reviewer will stop on. Retire or clearly mark these.
2. **`scripts/rtc_change_candidates.py --aoi-id` is unvalidated free text** (`:48`, required
   string, no cross-check against `geojson_path` or sha256). The script's geometry arrives solely
   via `--pre`/`--post` rasters. Nothing prevents stamping a **new** `aoi_id` onto **old**
   rasters, or the reverse. The AOI→raster binding exists only in `assembly_provenance.json`,
   which this script never reads. During an AOI transition this is a live mislabelling hazard,
   and it is the one code change this review would prioritise.

## Phase 4 — M6.12 FalkorDB design stage (design only; nothing built)

**Current state:** no FalkorDB, Neo4j or RedisGraph anywhere. The graph layer today is
**NetworkX** (`src/floodmap/network/graph.py`, `connectivity.py`, `candidate_disruption.py`).

**Honest positioning:** FalkorDB would add persistence, cross-run queryability, explicit
provenance edges and multi-scenario comparison. It would **not** add scientific capability that
NetworkX lacks for single-run connectivity. It is therefore a reasoning-and-evidence layer, and
it should be justified on that basis rather than as an analytical upgrade.

### 4.1 Proposed schema

Node labels — `:Road`, `:Intersection`, `:Bridge`, `:Settlement`, `:CriticalFacility`
(health/school/power), `:AoiVersion`, `:AcquisitionPair`, `:ChangeCandidate`, `:ExposureFinding`,
`:DisruptionScenario`, `:Recommendation`.

Relationships — `(:Road)-[:CONNECTS]->(:Intersection)`, `(:Road)-[:CARRIES]->(:Bridge)`,
`(:Settlement)-[:ACCESS_VIA]->(:Road)`, `(:ChangeCandidate)-[:INTERSECTS]->(:Road|:Bridge)`,
`(:ExposureFinding)-[:EVIDENCED_BY]->(:ChangeCandidate)`,
`(:DisruptionScenario)-[:ASSUMES_CLOSED]->(:Road)`,
`(:Recommendation)-[:DERIVED_FROM]->(:DisruptionScenario)`, and
`(:AoiVersion)-[:SCOPES]->(*)`.

### 4.2 Epistemic status as a mandatory property

Every node and edge carries `evidence_class`, constrained to exactly one of:

| Class | Meaning | Source |
|---|---|---|
| `observed_source` | Pre-event OSM / HydroRIVERS fact | authorised source |
| `sar_change_candidate` | Measured backscatter change | M6.3 |
| `inferred_exposure` | Spatial intersection | M6.4 |
| `hypothetical_scenario` | Assumed closure under a threshold | M6.5 |
| `model_recommendation` | Generated suggestion | reasoning layer |

This is the schema-level enforcement of AGENTS.md §8 and §16. A hypothetical closure must be
structurally incapable of being queried as an observed failure — the vocabulary rule should live
in the data model, not in a convention. Writes must reject any node lacking `evidence_class`.

### 4.3 Stable IDs, spatial provenance, versioning

- **IDs:** `osm:way/<id>`, `osm:node/<id>`, `hydrorivers:<HYRIV_ID>` for sourced entities;
  content-derived digests for computed ones (the M6.10 `aoi_id` pattern, which has already proved
  itself). Never positional or row-order IDs.
- **Spatial provenance:** every spatial node carries `geometry_wkt`, `crs` (explicit — EPSG:4326
  for delivery, EPSG:32645 for metric work), `source_snapshot_date` and `source_sha256`.
  No geometry without a CRS.
- **Versioning:** every node and edge carries `aoi_id` **and** `aoi_sha256`, plus
  `acquisition_pair_id`. A graph build is immutable and keyed by
  `(aoi_sha256, acquisition_pair_id, code_version)`. Changing the AOI creates a **new** graph
  version rather than mutating one — which is precisely the discipline whose absence makes §3.2
  a 20-row matrix.
- **Synchronisation:** one-directional, M6.4/M6.5 artifacts → graph. The graph is a derived
  projection and never a source of truth. A rebuild from artifacts must be byte-reproducible,
  verified the way `build_corridor_aoi.py --check` verifies the AOI.

### 4.4 Prerequisites — what must exist before population is meaningful

In strict order: **(1)** adopted AOI with a settled downstream justification; **(2)** authorised
pre-event OSM (roads, bridges, buildings, settlements) — *nothing graph-shaped exists without
this*; **(3)** real M6.4 exposure output; **(4)** real M6.5 disruption output with declared
thresholds; **(5)** the §3.5 Stage 10 consistency check passing.

**Today, items 2–4 do not exist.** Populating FalkorDB now would mean inventing nodes, which
AGENTS.md §3 and §11 forbid and which this review will not do. M6.12 should therefore deliver
**schema, ID scheme, evidence-class constraints, versioning rules, sync contract and tests
against fixtures** — and no populated graph.
