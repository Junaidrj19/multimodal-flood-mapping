# M6.4 — Infrastructure exposure to M6.3 SAR change candidates

**Status:** implemented and tested. **Blocked on real data:** no permitted
pre-event OpenStreetMap infrastructure layer exists in this checkout, and the
AOI is `UNVERIFIED`, so retrieving one is not authorised. The stage runs
end to end on the real M6.3 candidate mask and reports an explicit blocker for
the infrastructure half rather than fabricating inputs.

## Scope

This stage consumes the accepted M6.3 change-candidate outputs and reports
which pre-event OSM roads, buildings and settlements **spatially intersect
candidate regions**, and which lie in **never-observed** areas.

It deliberately stops before M6.5 road-network connectivity, and it draws no
routing or accessibility conclusion. It preserves the OSM identifiers and
attributes M6.5 needs so connectivity can consume these results unchanged.

The stage:

1. loads `rtc_change_candidates.tif` and `rtc_valid_mask.tif`, verifying the
   M6.3 stage tag, the declared `semantic_values` string, a projected
   metre-based CRS, explicit nodata, and exact grid alignment between the two
   rasters;
2. keeps **candidate**, **not_candidate** and **not_observed** pixels distinct
   throughout, and never treats not-observed as unaffected;
3. reads pre-event OSM layers **from disk only** — no retrieval;
4. verifies the recorded OSM snapshot is strictly before the event date, that
   the recorded event date matches the candidate mask's, and that the OSM
   extent actually overlaps the candidate raster;
5. reprojects every geometry into the candidate mask's CRS and measures a real
   geometric intersection — bounding boxes are recorded for the reader but are
   never the exposure test;
6. writes per-layer GeoJSON, a machine-readable summary, and linked provenance.

## Why a separate mask loader

The M6.3 candidate raster is **not** the frozen segmentation contract:

| | M4/M5 segmentation mask | M6.3 candidate mask |
|---|---|---|
| `0` | no water | not_candidate |
| `1` | permanent waters | **darkening_candidate** |
| `2` | floods | — (refused) |
| `255` | not observed | not_observed |

Loading the candidate raster through `load_flood_mask` would **succeed
numerically** — `0` and `1` are both legal segmentation values — and silently
reinterpret "darkening candidate" as "permanent water".
`src/floodmap/infrastructure/candidate_mask.py` exists so that cannot happen.
It validates the stage tag and the `semantic_values` tag, and rejects any value
outside `{0, 1, 255}`, including the segmentation `floods` id `2`.

No permanent-water label is created, and the candidate mask is not converted
into the three-class contract.

## Reuse rather than a parallel pipeline

Geometry measurement reuses the tested kernel in
`src/floodmap/infrastructure/exposure.py` (line sampling, `all_touched`
polygon rasterisation, threshold logic). Only the class being tested is
swapped, via `candidate_semantics()`. Every column and status the kernel
returns is then translated into candidate vocabulary, so no M6.4 artifact
contains the word "flooded" or a permanent-water quantity. A test asserts this.

## Status vocabulary

| Status | Meaning |
|---|---|
| `CANDIDATE_INTERSECTING` | Overlaps M6.3 darkening candidates by at least the configured threshold. Spatial coincidence with radar change evidence — **not** confirmed flooding or damage. |
| `UNOBSERVED` | No candidate intersection on observed pixels, but enough of the feature lies on not-observed pixels that a candidate there could not have been detected. |
| `NO_CANDIDATE_INTERSECTION` | Observed across the feature, and the candidate rule did not fire. **Not** evidence the feature was unaffected. |
| `OUTSIDE_CANDIDATE_GRID` | Lies entirely outside the candidate raster extent. |

## Configuration

`configs/candidate_exposure.yaml` records the stage parameters:

```text
line_sample_step_m        5.0    half the 10 m pixel
line_min_candidate_m     10.0    one pixel width
polygon_min_candidate_px    1
settlement_buffer_m       0.0    the containing pixel only
```

The thresholds deliberately mirror `configs/impact.yaml` (`exposure`) so
candidate intersection and flood-class exposure are directly comparable; a test
asserts the two stay in step. They are restated rather than imported so this
stage can be varied for sensitivity analysis without touching the segmentation
mask contract.

Retrieval is disabled in configuration (`inputs.osm.allow_download: false`) and
there is no default `layer_dir`, because a default path would imply layers exist
for an AOI nobody chose.

## Running the stage

```bash
.venv/bin/python scripts/candidate_exposure.py \
  --candidate-mask artifacts/m6_3/rtc_change_candidates/rtc_change_candidates.tif \
  --valid-mask artifacts/m6_3/rtc_change_candidates/rtc_valid_mask.tif \
  --osm-dir <directory holding pre-event osm_*.geojson> \
  --out-dir artifacts/m6_4/candidate_infrastructure_exposure
```

`--m63-summary` defaults to `rtc_change_summary.json` beside the candidate
mask; it supplies the scene identifiers, acquisition timestamps, orbit, AOI id
and event date that provenance carries forward.

`--osm-dir` must contain the layout `scripts/impact.py` already writes:

```text
osm_roads.geojson        required
osm_buildings.geojson    required
osm_settlements.geojson  required
osm_bridges.geojson      optional
osm_hubs.geojson         optional
osm_provenance.json      required (snapshot date, event date, AOI bbox)
```

### Exit codes

| Code | Meaning |
|---:|---|
| 0 | Exposure computed; artifacts written. |
| 1 | An input is invalid (wrong mask contract, misaligned rasters, post-event OSM snapshot, event-date mismatch, disjoint AOI). |
| 2 | Required pre-event OSM layers are absent. A blocker report is written and no exposure number is produced. |

## Outputs

Generated artifacts are local and git-ignored under
`artifacts/m6_4/candidate_infrastructure_exposure/`:

- `candidate_exposure_roads.geojson` — per-road `candidate_status`,
  `length_m`, `candidate_m`, `not_observed_m`, `not_candidate_m`,
  `outside_grid_m`, plus the source `osm_id`, `name`, `highway` and raw `tags`;
- `candidate_exposure_buildings.geojson` — per-building `candidate_status`,
  `pixels_touched`, `candidate_px`, `not_observed_px`, `not_candidate_px`;
- `candidate_exposure_settlements.geojson` — per-settlement `candidate_status`
  and the `settlement_buffer_m` used;
- `candidate_exposure_summary.json` — counts and lengths per status, per-highway
  candidate-intersecting length, candidate-mask QA, AOI association, data
  coverage and limitations;
- `candidate_exposure_provenance.yaml` — `infrastructure_exposure` record
  linking the Sentinel-1 scene pair, acquisition timestamps, OSM snapshot,
  processing operations, CRS, config version and limitations;
- `candidate_exposure_blocker.json` — written **instead** of the above when a
  required OSM layer is absent.

Features outside the candidate raster are retained and labelled
`OUTSIDE_CANDIDATE_GRID` rather than dropped, so the reader can see what was
excluded and why. GeoJSON is written in EPSG:4326 so it opens directly in QGIS.

## Interpreting the outputs

`candidate_m` is the length of a road lying on candidate pixels. It is a
measurement of spatial overlap with a rule-based Sentinel-1 γ⁰ darkening
observation. It is **not** flooded length, not damaged length, and not an
indication that the road is impassable. A flood mask intersecting a road is
evidence of spatial exposure, not of physical road destruction
(`AGENTS.md` §8).

`UNOBSERVED` must be read as missing information, not as good news. A road in
an unobserved area may or may not intersect a candidate region.

`NO_CANDIDATE_INTERSECTION` means the M6.3 rule did not fire there. Because
radar darkening is not unique to inundation and flooded vegetation or built-up
areas can be missed, this is not evidence the feature was unaffected.

## Blocker and the precise next step

`data/raw/osm/`, `artifacts/impact/` and any other pre-event OSM layer
directory are absent in this checkout. Obtaining them is an OSM retrieval, and
`AoiProvenanceStatus.UNVERIFIED` "permits geometry inspection and catalogue
metadata analysis only; it must not be used to authorise downloads"
(`src/floodmap/acquisition/aoi.py`). `AreaOfInterest.authorises_download` is
`false`. The gate was not bypassed and the AOI status was not changed.

To unblock, in order:

1. **Obtain a human authorisation for pre-event OSM retrieval.** The study
   extent question is closed: M6.15 adopted the human-approved corridor
   `trishuli-corridor-hydrorivers-v10-m615-2ae4183f` and recorded its producer,
   source, construction parameters and digests in its provenance sidecar.
   `provenance_status` remains `unverified` **precisely** so that adopting a
   geometry does not also authorise retrieval, so the missing decision is a
   separate, explicit OSM authorisation for this AOI — not a re-opening of the
   extent question.
2. **Fetch pre-event OSM** for an explicit pre-event snapshot, using the
   existing adapter (run without `--mask`, which performs OSM retrieval only):

   ```bash
   .venv/bin/python scripts/impact.py \
     --aoi-id <aoi-id> --aoi-bbox <min_lon> <min_lat> <max_lon> <max_lat> \
     --event-date 2026-08-26 --out <osm-dir>
   ```

   Run without `--mask`: that performs OSM retrieval only and writes
   `osm_*.geojson` plus `osm_provenance.json`. The snapshot resolves to
   00:00 UTC the day before the event, capped at the latest data ohsome holds.
3. **Re-run `scripts/candidate_exposure.py`** with `--osm-dir` pointing at that
   directory. No change to this stage is required. Exposure will then be computed
   only over the AOI-scoped valid support: roads and buildings in the unobserved
   36.63 % of the extent remain **unassessed** and must not be reported as
   unaffected.

## Limitations

Carried in every summary and provenance record:

- M6.3 candidates are rule-based Sentinel-1 RTC γ⁰ darkening evidence, not
  confirmed flood, damage or ground truth; intersection with them is spatial
  coincidence only.
- Radar darkening has causes other than inundation, and flooded vegetation or
  built-up areas can be missed entirely, so both false positives and false
  negatives are expected in the candidate mask.
- A candidate region intersecting a road or building is evidence of spatial
  exposure, not of physical destruction or structural failure.
- Not-observed pixels are reported as `UNOBSERVED` and never as unaffected.
- Infrastructure completeness is limited by OpenStreetMap coverage at the
  pre-event snapshot; unmapped features cannot appear.
- Settlement verdicts use a single representative point per settlement, so they
  describe that point and not the settlement's full built-up extent.
- The 10 m grid cannot resolve features narrower than one pixel, and building
  footprints use `all_touched` rasterisation, which is inclusive at edges.
- AOI provenance remains `UNVERIFIED`, so every count is relative to an extent
  whose origin is not established.
- No connectivity, routing or accessibility conclusion is drawn by this stage.

No DEM, segmentation checkpoint, validation product (EMSR927, Copernicus EMS,
UNOSAT) or post-event OSM was read. The M5 model was not used: no checkpoint or
fitted statistics are present, and γ⁰/σ⁰ radiometric compatibility has not been
established.

## Next stage

M6.5 road-network connectivity (`docs/m6.5-candidate-network-disruption.md`,
implemented) consumes `candidate_exposure_roads.geojson` together with
`candidate_exposure_settlements.geojson` and `candidate_exposure_summary.json`.
The preserved `osm_id`, `highway` and `tags` columns are exactly what
`floodmap.network.graph.build_road_network` reads, and the per-road
`candidate_m` / `not_observed_m` measurements are the quantities its closure
threshold acts on — optimistic (candidate only) and pessimistic (candidate plus
not-observed) variants are both available without re-measuring.

M6.5 treats closure as a stated hypothetical, not as something this stage
observed: nothing here establishes that a candidate-exposed road is impassable.
It remains blocked on the same missing pre-event OSM layers.
