# M6.7 — AOI Provenance Investigation and Authorization Readiness

**Scope.** Establish the documentary and technical provenance of the existing
Trishuli corridor AOI so the project owner can decide whether permitted
pre-event OSM acquisition may proceed.

**This document is evidence, not authorization.** No AOI status was changed, no
authorization check was altered or bypassed, and no satellite, OSM or catalogue
data was retrieved. See §8.

## 1. Executive finding

> ### INSUFFICIENT PROVENANCE — HUMAN INPUT REQUIRED

The polygon's origin **cannot be established from any evidence inside this
repository**, and a subsequent read-only search of the wider machine — shell and
Python histories, QGIS traces, every GeoJSON/shapefile/GeoPackage under
`~/Documents`, `~/Downloads` and `~/Desktop`, the Trash, the sibling checkout,
and the file's own macOS extended attributes — found **no producing evidence
either** (§9.1). Every question that bears on whether this geometry is the right
study extent resolves to an absence of record rather than to a disputed record.

Three things should be stated precisely, because they are easy to conflate:

1. **The geometry is technically sound.** It is valid, simple, closed, in the
   declared CRS family, and internally consistent to five significant figures
   (§4). Nothing in this investigation casts doubt on the *polygon as a
   polygon*.
2. **The geometry's provenance is absent, not merely incomplete.** There is no
   author, no tool version, no generation date, no source centreline, no
   generating script, and no Git history — in this checkout or the sibling one
   (§3, Q1–Q4). The file is machine-generated by something nobody has
   identified.
3. **Internal consistency is not provenance.** The file agrees with itself
   because it was produced by one tool in one pass. That is evidence about *how
   it was written*, not about *what it was computed from* or *whether that was
   the right thing to compute*. A 1 km buffer of the wrong centreline would be
   exactly as internally consistent as a 1 km buffer of the right one.

The determinative point for the stated objective: pre-event OSM acquisition is
*extracted within an AOI*. Running it against this polygon would commit the
project's infrastructure-exposure and connectivity results to a study extent
nobody has chosen. That is the governance hazard `docs/dataset-registry.md`
§1.6 was written to prevent, and it is unchanged by this investigation.

**One new technical finding this investigation adds** (not recorded in §1.6 or
§1.6.1): the polygon is very likely **not an unmodified buffer output** — it
carries a single 2,803 m straight edge at its south-western terminus consistent
with a straight clip, while its north-eastern terminus does not (§4.4). This
*adds* a provenance question rather than answering one.

**Authorization enforcement was audited and found intact** — three independent
gates, all currently closed, covered by existing tests (§5). **No authorization
defect was found, so no new tests were added and no code was changed** (§7).

### 4.3 Buffer substantiation — what can and cannot be concluded

The source centreline is **absent from the repository** (glob for `*.shp`,
`*.gpkg`, `*centre*`, `*center*`, `*centreline*`, `*river*` → NONE FOUND), so
the 1 km buffer **cannot be independently substantiated**. The following probes
constrain the hypothesis without confirming it.

Morphological erosion in EPSG:32645:

| Erode by | Empty? | Residual area | Parts |
|---|---|---|---|
| 1,000 m | No | 3.6229 km² | 14 |
| 1,005 m | No | 3.0727 km² | 35 |
| 1,010 m | No | 2.6173 km² | 45 |
| 1,050 m | No | 0.9434 km² | 16 |
| 1,100 m | No | 0.3070 km² | 6 |
| 1,200 m | No | 0.0007 km² | 2 |

Maximum inscribed circle: **radius 1,200.69 m** centred at
`lon 85.15201, lat 27.93217`. The largest residual lobe (2.5977 km², 72 % of the
total residual) is centred at `85.14979, 27.93406` — the same place.

**Why this is not a contradiction of the 1 km claim.** A 1 km buffer of a
*single simple line* would erode to empty at 1,000 m and have a maximum
inscribed radius of exactly 1,000 m. This polygon does not. But the file
declares **two rivers** (Bhote Koshi, Trishuli), and where two 1 km-buffered
branches meet at interior angle θ the union is locally wider, with inscribed
radius `1000 / sin(θ/2)`:

| θ | predicted radius |
|---|---|
| 110° | 1,220.8 m |
| **112°** | **1,206.2 m** |
| 115° | 1,185.7 m |

The measured 1,200.69 m corresponds to θ ≈ 112°, and the 14 residual lobes are
the 14 places where branches or meanders approach within 2 km. **This is the
expected signature of a 1 km buffer of a branching network.**

**Conclusion, stated conservatively.** The geometry is *consistent with* a 1 km
buffer of a multi-branch centreline, and is *inconsistent with* a 1 km buffer of
a single simple line. It does **not** substantiate that the buffer distance was
1,000 m, because the source geometry needed to check that is unavailable. No
claim that the buffer is correct is made here.

## 5. Authorization enforcement findings

**Finding: enforcement is intact, layered, and currently closed on all three
gates. No defect was found.**

`scripts/acquire.py::_authorise_download` (lines 294–362) is invoked at
`scripts/acquire.py:398`, documented and confirmed to run **before any catalogue
request**, so an unauthorized run fails fast rather than after issuing queries.

| # | Gate | Implementation | Current state |
|---|---|---|---|
| 1 | explicit `--download` CLI flag | `scripts/acquire.py:317` | not passed |
| 2 | `acquisition.download.enabled` | `scripts/acquire.py:319-325` | **`false`** (`configs/data.yaml:211`) |
| 3 | AOI provenance | `scripts/acquire.py:326` → `AreaOfInterest.authorises_download` (`src/floodmap/acquisition/aoi.py:326-337`) | **`False`** (status `unverified`) |
| 3b | narrow operator exception | `scripts/acquire.py:333-355`, `ExploratoryDownloadAuthorisation` | **disabled** — default `False` (`src/floodmap/acquisition/config.py:281-285`); **no such block exists in `configs/data.yaml`** |

Properties worth recording:

- `authorises_download` returns `True` **only** for `VERIFIED`
  (`aoi.py:337`) — `UNVERIFIED` and `SYNTHETIC` both deny.
- The default status is `UNVERIFIED` by construction (`aoi.py:272-279`), so an
  AOI is unverified by omission rather than by oversight.
- Gate 2 was a real historical defect, now fixed and documented: the
  `enabled` key existed but **no production code read it**
  (`scripts/acquire.py:302-307`). It is now enforced.
- The exception path (3b) does **not** promote provenance: the AOI stays
  unverified and disclosures keep firing (`scripts/acquire.py:329-332`). It is
  additionally pinned to a specific AOI sha256 and refuses to carry over to a
  different geometry (`scripts/acquire.py:349-355`).
- Disclosure propagates into the manifest: `provenance_limitations()`
  (`aoi.py:339-365`) emits 6 lines for this AOI — the UNVERIFIED warning, the
  source sha256, and all 5 provenance gaps (reproduced live).
- Downstream consumers enforce the same gate independently, e.g.
  `artifacts/m6_4/…/candidate_exposure_blocker.json:19-21` records
  `authorises_download: false` with the governing rule quoted.
