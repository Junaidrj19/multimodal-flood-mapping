# M6.3 — Real RTC change-candidate vertical slice

**Status:** implemented and exercised on the existing local Sentinel-1 RTC
pre/post pair.

## Scope

This stage advances the workflow from accepted M6.2 RTC pixel preparation to
representation-aware pre/post change evidence. It deliberately stops before
M5 inference, infrastructure exposure, road disruption, connectivity, and
dashboard wiring.

The stage:

1. reads the existing assembled VV/VH GeoTIFFs without downloading imagery;
2. verifies named VV/VH bands, explicit nodata, shared CRS/transform/resolution/
   extent/pixel alignment, and the declared `gamma0_linear_power` convention;
3. computes VV and VH log-ratio change in dB from the source linear γ⁰ power;
4. propagates invalid, non-finite, and non-positive-power pixels as invalid;
5. writes an exploratory candidate mask where both polarisations darken by at
   least the configured threshold; and
6. writes georeferenced outputs, statistics, acquisition timestamps, pair
   identity, and provenance.

The output is **change-candidate evidence only**. It is not confirmed flood,
damage, ground truth, or an accuracy measurement.

## Configuration and rule

`configs/rtc_change_candidates.yaml` records the stage parameters:

```text
VV change <= -3 dB AND VH change <= -3 dB
```

These are explicit exploratory γ⁰ change thresholds. They are not imported from
the M5 σ⁰ contract, are not fitted to a validation product, and do not establish
model equivalence.

  --pre data/raw/sentinel1_rtc/pre_S1D_IW_GRDH_1SDV_20260816T122141_20260816T122206_004151_007980_rtc_VVVH_aoi.tif \
  --post data/raw/sentinel1_rtc/post_S1D_IW_GRDH_1SDV_20260828T122141_20260828T122206_004326_007FA4_rtc_VVVH_aoi.tif \
  --out-dir artifacts/m6_3/rtc_change_candidates \
  --aoi-id trishuli-corridor-UNVERIFIED-9035eeee \
  --event-date 2026-08-26 \
  --pre-scene-id S1D_IW_GRDH_1SDV_20260816T122141_20260816T122206_004151_007980_rtc \
  --post-scene-id S1D_IW_GRDH_1SDV_20260828T122141_20260828T122206_004326_007FA4_rtc \

## Outputs

Generated artifacts are local and git-ignored under
`artifacts/m6_3/rtc_change_candidates/`:

- `rtc_change_features.tif` — georeferenced `vv_change_db` and `vh_change_db`;
- `rtc_change_candidates.tif` — `0=not_candidate`, `1=darkening_candidate`,
  `255=not_observed`;
- `rtc_valid_mask.tif` — `1=inside the configured AOI with a valid pre/post
  VV+VH change`, `0=outside the AOI or not observed` (0.2.0 semantics);
- `rtc_aoi_mask.tif` — `1=pixel centre inside the configured AOI`, `0=outside`
  (added in 0.2.0; required, so "outside the extent" stays distinguishable
  from "inside the extent but unobserved");
- `rtc_change_summary.json` — machine-readable QA, distributions, rule, pair
  metadata and the `aoi_scope` block with its named denominators;
- `rtc_change_features_provenance.yaml`;
- `rtc_change_candidates_provenance.yaml`.

## Limitations and next blocker

The pair is same relative orbit 85 and ascending, but the AOI remains
`UNVERIFIED` as required by the acquisition milestone. No DEM-derived slope
mask, independent validation, ground truth, or learned checkpoint was used.
Radar darkening is not unique to inundation, and the candidate mask does not
support a confirmed flood-damage claim.

The next coherent stage can only promote these candidates into the existing
infrastructure/network consumers after an explicit class-mask contract is
selected and validated. M5 inference remains blocked because no existing
checkpoint and fitted statistics were found; this stage does not train a
replacement. Pre-event OSM retrieval and dashboard/report integration remain
subsequent stages.
